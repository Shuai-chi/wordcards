# WordForge AI 色彩指令列設計

**日期：** 2026-07-23  
**狀態：** 已實作；2026-07-23 Windows 驗收修訂已核准，修訂中  
**範圍：** 設定視窗「外觀 → 顏色搭配 → 自訂配色」的指令匯入、目前配色匯出、即時預覽、最近儲存配色回復與相關驗證；不新增後端、雲端功能或主題儲存格式。

## 1. 目標

1. 讓使用者可請 AI 產生一行固定格式的配色指令，貼入設定後一次修改全部或指定顏色。
2. 嚴格驗證指令，任何一段有錯時不得套用半套修改。
3. 讓使用者可把目前配色顯示成標準指令，並一鍵複製供分享或交給 AI 修改。
4. 打勾只套用現有即時預覽；沿用設定視窗頂部「儲存」作為唯一正式持久化動作。
5. 回復按鈕捨棄目前模式尚未儲存的顏色修改，回到最近一次正式儲存的配色。
6. 沿用現有主題、對比檢查、未儲存保護、localStorage 與備份資料邏輯。

## 2. 已確認的產品決策

- 採用獨立純函式解析／序列化模組，不把語法細節堆進 `SettingsModal`。
- 指令只作用於目前正在編輯的淺色或深色模式；兩個模式須分別切換、分別套用。
- 採語系無關的固定英文鍵與 ASCII 分號，不接受中文鍵、縮寫別名、JSON 或任意 CSS。
- 允許只指定部分顏色；未指定項目維持目前值。
- 任何項目無效時整行不套用，並指出錯誤段落與原因。
- 語法正確但對比不足時仍更新即時預覽；沿用現有警告並禁止正式儲存。
- 回復只回到最近一次正式儲存的配色，不提供多版本歷史堆疊。
- 指令文字是暫態編輯資料，不持久化；解析後的主題顏色沿用現有儲存機制。

## 3. 指令格式

### 3.1 標準格式

完整指令範例：

```text
background=#F7F8FC;card=#FFFFFF;primary=#4F46E5;accent=#F59E0B
```

部分指令範例：

```text
primary=#2563EB;accent=#F59E0B
```

### 3.2 文法

- 合法項目只有 `background`、`card`、`primary`、`accent`。
- 項目名稱與色碼間固定使用半形等號 `=`。
- 多個項目固定使用半形分號 `;` 分隔；分號後可有空白。
- 色碼固定為 `#` 加六位十六進位字元；輸入接受大小寫，內部及匯出統一為大寫。
- 每行可有 1～4 個項目，順序不限。
- 可忽略整行、項目名稱及色碼前後的空白。
- 不接受重複項目、多行、空白項目、結尾分號、三位 HEX、`rgb()`、CSS 變數、中文項目名稱、縮寫或其他分隔符。
- 指令不得執行或插入任意 CSS，只能映射到四個既有 `ThemeCoreTokens` 欄位。

### 3.3 標準匯出

匯出固定遵循以下規則：

1. 順序為背景 → 卡片 → 主色 → 強調。
2. 一律輸出全部四項。
3. 色碼一律為大寫六位 HEX。
4. 不輸出多餘空白或結尾分號。

## 4. 介面設計

色彩指令列放在「外觀 → 顏色搭配 → 自訂配色」現有四個色彩欄位上方，只在自訂配色編輯區顯示。

### 4.1 操作區

- 標題：`AI 色彩指令`。
- 輔助操作：`顯示目前配置`、`一鍵複製`。
- 單行可編輯輸入格。
- 輸入格右側：打勾圖標與回復圖標。
- 規則提示：

```text
Format: key=#RRGGBB; key=#RRGGBB｜Keys: background=背景, card=卡片, primary=主色, accent=強調｜可只填要修改的項目
```

- 規則下方顯示成功、錯誤、複製結果或對比警告狀態。

### 4.2 操作行為

- `顯示目前配置`：把目前模式預覽中的完整配色，以標準格式填入輸入格。
- `一鍵複製`：直接複製目前模式預覽中的完整標準指令，不覆蓋輸入格內尚未送出的草稿。
- 打勾：解析整行並在成功時套用即時預覽。
- Enter：等同打勾；多行輸入仍視為格式錯誤。
- 回復：只恢復目前編輯模式最近一次正式儲存的配色。
- 成功套用後保留原輸入文字，方便使用者繼續修改；只有「顯示目前配置」會改寫成完整標準格式。
- 切換淺色／深色編輯模式時，清空指令輸入及驗證訊息，避免誤套上一模式的指令。

### 4.3 響應式與可用性

- 桌面與寬容器維持單列指令操作；窄容器允許輔助操作及輸入列合理換行。
- 輸入格使用 `min-width: 0` 並取得主要可用寬度，不產生水平捲動。
- 打勾及回復按鈕維持至少 44px 的觸控區域。
- 圖標按鈕具有中文 tooltip／可見標籤、`aria-label`、hover、active 與 focus-visible 狀態。
- 驗證與剪貼簿訊息使用 `aria-live`，避免只靠顏色傳達結果。

## 5. 元件與模組邊界

### 5.1 `themeCommand` 純函式模組

新增無 React、無 DOM、無 storage 副作用的深模組，單一管理：

- 固定英文鍵與 `ThemeCoreTokens` key 的對照。
- 固定順序。
- 嚴格解析與原子驗證。
- 六位 HEX 正規化。
- 結構化錯誤資訊。
- 完整標準指令序列化。

對外介面保持精簡：輸入字串得到成功的部分 token patch，或失敗的結構化錯誤；輸入完整 tokens 得到標準字串。語法與文案所需 metadata 不散落在 React 元件中。

### 5.2 `ColorCommandBar` 呈現元件

新增小型呈現／互動元件，負責：

- 輸入狀態。
- 顯示、複製、打勾與回復控制。
- 成功／錯誤訊息呈現。
- 鍵盤與可及性行為。

元件不直接讀寫 `localStorage`，也不自行決定淺色／深色或持久化基準；目前 tokens、是否可回復及 callback 由父層提供。

### 5.3 `SettingsModal` 整合責任

`SettingsModal` 負責：

- 提供目前 `editorMode` 與 `coreTokens`。
- 把成功解析的部分 patch 合併到目前 tokens。
- 透過既有 `setCustomTheme()` 與 `previewAppearance()` 更新預覽。
- 從 `savedSnapshot.appearance[editorMode]` 恢復目前模式最近儲存的完整 selection，包含預設或自訂狀態。
- 沿用既有 `getThemeContrastIssues()`、dirty comparison、全域儲存與離開保護。

## 6. 資料流與持久化

### 6.1 套用指令

1. 使用者輸入指令並按打勾或 Enter。
2. `themeCommand` 解析整行。
3. 失敗時只回傳錯誤，不產生 patch、不修改預覽。
4. 成功時把部分 patch 合併到目前模式 `coreTokens`。
5. 使用既有 `setCustomTheme()` 產生下一份 `draftAppearance`。
6. 使用既有 `previewAppearance()` 同步設定草稿與 App 層即時預覽。
7. 實際顏色有變化時，既有 dirty comparison 自然判定為未儲存變更。

### 6.2 儲存

- 設定視窗頂部「儲存」仍是唯一正式保存動作。
- 儲存成功後沿用目前 `withAppearanceTimestamp()`、`onSave()` 與 `setSavedSnapshot()` 流程。
- 儲存成功後設定視窗保持開啟，當下配色成為新的回復基準。
- 正式資料繼續寫入 `wordforge_appearance_v1`，不增加新的 localStorage key 或 schema version。
- 現有備份保存的是解析後的外觀設定，無須保存指令文字或修改備份格式。

### 6.3 回復

- 回復只替換 `draftAppearance[editorMode]` 為 `savedSnapshot.appearance[editorMode]`。
- 保留目前的模式選擇與另一模式的草稿。
- 不影響字體、倍率、圖標、每日上限或其他尚未儲存的設定。
- 回復後立即更新 App 層預覽，dirty 狀態依完整草稿與 snapshot 的實際差異重新計算。
- 不建立 undo stack，也不跨越最近一次成功儲存。

### 6.4 匯出與剪貼簿

- 顯示與複製皆以目前預覽中的 `coreTokens` 為來源，因此可包含尚未正式儲存但已成功套用的修改。
- 使用瀏覽器 Clipboard API；成功與失敗皆顯示可讀狀態。
- 瀏覽器拒絕剪貼簿權限時不宣稱成功，也不靜默吞掉錯誤。

### 6.5 WSL IP 與非安全來源相容性

- 備份匯出不得假設 `crypto.randomUUID()` 或 `crypto.subtle` 一定存在。
- UUID 優先使用原生 `randomUUID()`；不可用時，以仍可用的 `crypto.getRandomValues()` 產生 RFC 4122 v4 UUID。
- SHA-256 優先使用原生 `crypto.subtle.digest()`；不可用時，使用專案內可測試的純 TypeScript SHA-256 fallback，雜湊格式及既有備份 schema 保持不變。
- 不降低備份驗證強度、不改用非 SHA-256 雜湊，也不新增後端或 HTTPS 憑證依賴。

## 7. 驗證與錯誤處理

### 7.1 原子驗證

以下任一情況使整行失敗：

- 空字串或多行內容。
- 缺少項目名稱、等號或色碼。
- 未知項目。
- 重複項目。
- 錯誤分隔符、空白段落或結尾分號。
- 非六位 HEX 或包含非法字元。

錯誤包含段落索引、原始片段與可讀原因，例如：

```text
第 2 段「primary=#12GG44」：色碼必須是六位 HEX。
```

未知項目需同時列出四個合法名稱；重複項目需指出首次與重複位置。錯誤狀態下不得呼叫預覽更新 callback。

### 7.2 對比不足

- 語法正確與可讀性對比是兩層不同驗證。
- 語法正確時先更新預覽，再由既有 `getThemeContrastIssues()` 產生警告。
- 有對比問題時沿用既有機制停用頂部正式儲存。
- 使用者可繼續修改指令或既有色彩欄位直到警告消失。

### 7.3 Dirty 與暫態狀態

- 單純輸入或修改指令文字不算未儲存設定。
- 只有成功套用且造成實際外觀差異才影響 dirty 狀態。
- 關閉設定時不保留指令輸入、解析訊息或複製訊息。
- 有實際配色差異時，沿用目前離開確認與捨棄預覽回復流程。

## 8. 測試與驗收

### 8.1 解析器單元測試

- 完整四項指令成功。
- 1～3 項部分指令成功，未指定項目不出現在 patch。
- 任意順序與允許的前後空白成功。
- 小寫 HEX 輸入正規化為大寫。
- 未知、重複、缺值、三位 HEX、非法 HEX、多行、全形分號、結尾分號與空白段落失敗。
- 任一段錯誤時不回傳可套用的部分 patch。
- 完整 tokens 以 `background` → `card` → `primary` → `accent` 匯出，且匯出結果可再次解析。
- 中文鍵、縮寫、全形分號、未知鍵與其他既有錯誤情境均原子拒絕。

### 8.2 設定介面測試

- 打勾與 Enter 成功更新目前模式預覽。
- 無效指令完全不改變 `draftAppearance` 或 App 層預覽。
- 部分指令只修改指定項目。
- 回復還原目前模式最近一次成功儲存的 selection，不影響另一模式與其他設定。
- 儲存後當下配色成為新的回復基準。
- 淺色與深色指令互不影響，切換模式清空暫態指令狀態。
- 顯示目前配置填入完整標準字串。
- 一鍵複製不覆蓋輸入草稿，並處理 Clipboard 成功與拒絕。
- 對比不足時可看到預覽與警告，但正式儲存維持停用。
- 只有實際配色差異觸發未儲存提醒。

### 8.3 持久化與相容性

- 正式儲存後重新整理仍保留配色。
- 指令文字與狀態不跨重新整理保留。
- 現有備份匯出／匯入仍可保存主題結果，不需 schema migration。
- 在 `isSecureContext=false`、`crypto.randomUUID` 與 `crypto.subtle` 缺失但 `getRandomValues` 可用時，備份仍可下載並通過自身驗證。
- 既有預設配色、手動色彩欄位、字體、圖標、練習與統計邏輯不受影響。

### 8.4 響應式人工檢查

- 320、390、430、768、1024、1440px。
- 手機直式與矮橫式。
- 操作列可合理換行，無水平捲動、按鈕遮蔽或不可達內容。
- 打勾與回復至少 44px，鍵盤 focus 可見，錯誤不只靠顏色辨識。

### 8.5 專案驗證

實作完成後執行 `package.json` 實際存在的 lint、typecheck、test 與 build 指令；不存在的 script 必須如實註明，不得虛構結果。

## 9. 非目標

- 不新增 AI API 或由應用程式直接呼叫模型。
- 不新增後端、登入、雲端同步或第三方解析套件。
- 不接受任意 CSS、JSON、中文鍵、英文縮寫別名或寬鬆自然語言解析。
- 不新增多版本配色歷史、跨模式單一指令或自動修正對比。
- 不更換既有主題 schema、localStorage key、備份格式或外觀預設。
- 不重寫整個設定視窗或其他頁面。
