# Module 7｜PMP 專案管理(第 10 週)

## 🎯 學習目標
- 理解 PMP/PMI 專案管理的基本框架
- 熟悉專案生命週期與五大流程組
- 認識十大知識領域的核心概念
- 能寫出 WBS(工作分解結構)與風險登記表
- 理解 Agile/Scrum 與傳統瀑布式管理的差異與適用場景

## 1. 為什麼工程師要懂專案管理

寫程式做出功能只是專案的一部分,真實世界的軟體/AI 專案常常因為「範疇蔓延、時程失控、風險沒被提前識別」而失敗,而不是技術能力不足。懂 PM 方法論能幫助你:
- 把模糊的需求拆解成可執行的任務(呼應 Module 1–8 的模組化拆分思維)
- 提前識別風險(例如「API 額度可能不夠用」「LINE 審核可能延遲」)
- 用時程與資源估算,合理溝通交付日期

**PMP(Project Management Professional)** 是 PMI(Project Management Institute)發行的專案管理證照,其知識體系來自《PMBOK 指南》,是業界最通用的專案管理語言。

## 2. 專案生命週期與五大流程組

一個專案不論大小,都會經歷五個流程組(不是線性一次性,而是會反覆疊代):

```
啟動(Initiating) → 規劃(Planning) → 執行(Executing) → 監控(Monitoring & Controlling) → 結束(Closing)
                          ↑______________________________|
                          (監控貫穿整個執行期間,發現偏差就回頭調整規劃)
```

- **啟動**:定義專案目的、範疇、關鍵利害關係人(以 Capstone 專案為例:「打造一個 AI 客服系統,目標是自動回答 80% 常見問題」)
- **規劃**:拆解任務(WBS)、排時程、估成本、識別風險
- **執行**:實際開發(對應 Module 1–8 的技術實作)
- **監控**:追蹤進度是否符合計畫,發現落後或風險發生時調整
- **結束**:驗收交付物、整理經驗教訓(Lessons Learned)

## 3. 十大知識領域概觀

| 知識領域 | 核心問題 | 對應到軟體專案的例子 |
|---|---|---|
| 整合管理 | 如何讓所有部分協調一致? | 制定專案章程,統籌各模組進度 |
| 範疇管理 | 到底要做什麼、不做什麼? | 明確定義「客服機器人只回答訂單與退貨問題」,避免範疇蔓延 |
| 時程管理 | 什麼時候完成? | 用 WBS 拆解任務並排出甘特圖 |
| 成本管理 | 預算多少? | 估算 AWS/OpenAI API 費用,設定預算上限(呼應 Module 4、5) |
| 品質管理 | 怎麼確保做出來是對的? | 定義測試案例,例如機器人準確率門檻 |
| 資源管理 | 誰來做、需要什麼工具? | 確認開發者技能、環境(呼應 Module 1 的環境設置) |
| 溝通管理 | 誰需要知道什麼、多常回報? | 每週進度同步會議或報表 |
| 風險管理 | 可能出什麼問題? | API 服務中斷、審核延遲、成本超支等 |
| 採購管理 | 需要外部資源/廠商嗎? | 選擇 OpenAI vs 其他 LLM 供應商的評估 |
| 利害關係人管理 | 誰在乎這個專案的結果? | 使用者、主管、維運團隊各自的期待 |

## 4. WBS(工作分解結構)

把大目標拆解成可管理、可估算工時的小任務,是規劃的核心工具:

```
1. AI 客服系統 Capstone 專案
   1.1 後端開發
       1.1.1 設計資料庫 schema(對應 Module 2)
       1.1.2 開發 ChatGPT API 整合(對應 Module 4)
       1.1.3 開發 FastAPI 服務(對應 Module 4)
   1.2 前端整合
       1.2.1 LINE Bot Webhook 開發(對應 Module 6)
       1.2.2 Flex Message 設計
   1.3 部署與維運
       1.3.1 Docker 容器化(對應 Module 5)
       1.3.2 部署到 AWS(對應 Module 5)
       1.3.3 監控與日誌設定
   1.4 分析與報表
       1.4.1 Power BI 使用量儀表板(對應 Module 3)
   1.5 專案管理文件
       1.5.1 WBS 與時程規劃
       1.5.2 風險登記表
```

**WBS 拆解原則**:每個最底層任務(work package)應該可以在合理時間內(例如 1–3 天)完成,且有明確的「完成」定義,不要拆得過細或過粗。

## 5. 風險管理

風險管理不是「等問題發生再處理」,而是**提前識別、評估、規劃應對策略**:

| 風險 | 發生機率 | 影響程度 | 應對策略 |
|---|---|---|---|
| OpenAI API 額度超支 | 中 | 高 | 設定用量上限、加上快取降低重複呼叫(呼應 Module 4） |
| LINE 官方帳號審核延遲 | 中 | 中 | 提前 2 週申請,先用個人帳號測試開發 |
| AWS 免費額度用完產生費用 | 低 | 中 | 設定 Billing Alert(呼應 Module 5） |
| 資料庫設計後期需大改 | 中 | 高 | 開發前先做完整需求訪談與 ER 圖設計(呼應 Module 2） |

四種常見應對策略(ETPA):
- **規避(Avoid)**:改變計畫消除風險
- **降低(Mitigate)**:降低發生機率或影響
- **轉移(Transfer)**:例如買保險、外包給有經驗的廠商
- **接受(Accept)**:影響小,先記錄,發生了再處理

## 6. Agile / Scrum 與傳統瀑布式的對照

| | 瀑布式(Waterfall) | Agile / Scrum |
|---|---|---|
| 需求 | 前期完整定義,變動成本高 | 允許逐步演進(透過 Sprint) |
| 交付方式 | 專案結束一次性交付 | 每個 Sprint(通常 1–2 週)交付可用增量 |
| 適合場景 | 需求穩定、法規/合約導向的專案 | 需求會隨市場回饋調整的產品開發 |
| PMBOK 對應 | 傳統五大流程組線性執行 | PMBOK 也涵蓋 Agile 方法(混合式方法) |

實務上很多團隊採用「混合式(Hybrid)」:整體專案用 WBS/時程做宏觀規劃,日常開發則用 Scrum 的 Sprint、每日站會、看板(Kanban)來管理迭代節奏。本課程的 Capstone 專案也建議你用「輕量 Scrum」節奏:每週當作一個 Sprint,對照 [`00-syllabus.md`](../00-syllabus.md) 的檢核點驗收。
